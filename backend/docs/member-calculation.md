# Original-flow member lookup and calculation

`POST /api/demo/member-lookup` accepts a strict `{memberId, dateOfBirth}` pair. Both fields are required; birth dates must be real calendar dates. A match returns the existing synthetic `MemberData` payload, including the exact linked plan and a nullable procedure card. Unknown IDs and incorrect birth dates both return `200 {"matched":false}` without member or plan details. Invalid inputs return 422; unavailable data returns 503. The internal alternative `{displayName, dateOfBirth}` matches only a normalized full name and rejects ambiguity.

`POST /api/calculate` accepts the original confirmed scenario plus optional `memberIdentity: {memberId, dateOfBirth}`. When present, the server reloads the member and linked plan before calculation. Stored current usage, deductible, limits and category shares override browser values. Enrollment dates constrain scheduling. Future-year usage remains an explicit user-confirmed assumption because the stored snapshot describes the current year. Guest manual and sample calculations use their confirmed inputs and do not read the database.

The user selected a labeled conservative estimate for incomplete pending and rollover terms. Projected pending plan payments reserve current base capacity separately from settled usage; the stored deductible remaining stays unchanged because pending deductible impact is unknown. The current rollover bank is displayed separately and excluded from payments. Prospective awards are not modeled. A missing pending projection, stale or unverified source, unreconciled balances, or an unsupported linked plan blocks calculation rather than using guest values.

For Parker `SYN-MEMBER-0002` / `2018-02-28`, the stored snapshot has base maximum 200,000 cents, settled usage 27,710, base remaining 172,290, projected pending reserve 9,300, deductible remaining 2,500 and rollover bank 30,000. Modeled current base availability is 162,990 cents. `memberBenefitContext.status` is `CONSERVATIVE`; the bank remains excluded. Ledger `maximum.usedBeforeCents` remains 27,710 and additive `maximum.reservedBeforeCents` records the separate reserve. Event calculation steps explain the available cap. This is a modeled estimate, not a guaranteed upper bound: adjudication and eligibility changes can alter costs.

Validation: targeted member identity, original calculation and HTTP wiring tests cover paired matching, ambiguity, no-match privacy, strict input and revision checks, null treatment cards, server overrides, distinct member plans, pending reserves, excluded banks, unknown projections, source status and coverage dates.
